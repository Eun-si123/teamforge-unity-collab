# P1 M5 signed metadata/Active pointer write durability — 2026-11-24

**Scope:** Implementation and source/Node tests in integration Draft #620. This is a historical work checkpoint, not a promotion of `FIELD_BLOCKED` release readiness. Current canonical readiness remains `../STATUS.md`.

## Actual failure surfaces

- Signed content-addressed Manifest and Descriptor files were written directly to their final immutable `.json` names. A process crash while `writeFile` was in progress could leave a truncated *final-name* file; a later retry would see `EEXIST` and refuse the mismatched source indefinitely. Reading that draft file was never an authorized shortcut to approval, but corrupted final-name debris could block normal project publishing/recovery.
- Owner identity and Project UUID creation already used temporary files and exclusive hard links, but did not `fsync` their source bytes before publishing final names. Losing the only Owner key or Project UUID metadata after approval would be a major availability problem.
- Host `published.json` and Guest `current.json` were atomically renamed into place but not explicitly flushed. On POSIX, the Active folder rename also lacked a directory flush before publishing the new Guest current pointer. Atomic visibility alone is not a power-failure durability guarantee.

## Implemented guarded writes

- Added `project-peer/src/persistent-metadata.mjs`. It creates unique `0600` temporary JSON files, fully writes and **file-syncs** them, then installs immutable signed metadata with **exclusive hard links**. Existing exact canonical bytes are accepted idempotently; mismatched, truncated, or symlinked final files fail closed. Existing-files verification uses bounded, pinned descriptor/handle reads with no-follow where available and a path identity recheck. Interrupted partial temp names are never selected as canonical metadata.
- Project UUID metadata uses the same flushed exclusive installer. Owner private identity saves now file-sync before linking and flush the containing POSIX directory after identity installation; never replaces an existing key.
- Host approved `published.json`, Guest `current.json`, and other Peer pointer/invite uses create a flushed temporary JSON and atomic rename; on POSIX, the containing directory is then `fsync`ed. Guest Active directory entry is likewise synced after moving verified staged bytes into Active and *before* writing the new canonical `current.json` pointer. If an activation error occurs after the final filesystem-mutation boundary, the Guest staging status remains `Activating` with `recoveryRequired:true`, **not** a false `Rejected` claim: the new Active may already exist and the verified current pointer must be inspected before any retry.
- A post-rename/link directory sync failure reports `metadata_durability_unconfirmed`: the target **may already have advanced** and must be inspected before retry. It must **never** be reported as a clean rollback. POSIX directory fsync is mandatory for claimed local success; on Windows Node does not provide a portable directory fsync, so the implementation flushes file data but retains the platform/volume power-cut uncertainty. Network/unusual filesystems remain fail-closed where flush/link operations are unsupported.
- No product version, protocol, schema, Project signature rule, external Live Baseline command, trust gate or automatic M4→M5 transition is introduced.

## Verification and limitations

- `project-peer/test/persistent-metadata.test.mjs`: explicit idempotent concurrent writes and immutable inode, corrupt/partial file refusal, symlink refusal, exclusive Project identity creation, orphan temp ignored, complete pointer swap, and subprocess `SIGKILL` after committed writes; exercised with existing Project Engine signed approval tests. `identity-file-safety.test.mjs` injects an actual partial `FileHandle.writeFile` failure and verifies no private temporary remains. `managed-project.test.mjs` injects a failure **after a real Guest Active rename** and confirms prior Active preservation, recovery-required status and a safe refusal to overwrite the already-moved revision.
- Linux actual kernel syscall evidence was observed with `strace`: each file `fsync` succeeded, each exclusive `link` or pointer `rename` succeeded, and the parent directory `fsync` succeeded. This is **not** a physical power-cut or Windows filesystem guarantee.
- Exact local source after these changes (Ubuntu Mini PC, Node 24): full Project Peer **645 PASS / 0 FAIL / 6 environment SKIP** (651 total), full Server **464 PASS / 0 FAIL**, cross-Phase **143 PASS / 0 FAIL**; suite counts overlap. Host/Seed smoke, engineering, docs, workflow policies and public source validators PASS. The pre-existing Owner-key partial-write negative test was adapted to inject errors into the real `FileHandle.writeFile` path; the Guest post-Active-rename error injection verifies `recoveryRequired:true` without mislabeling a rollback. Exact new-commit GitHub CI must be checked after push. Do not claim an end-to-end durability transaction across Coordinator SQLite, the Host published pointer and Guest Active; M4→M5 still requires Editor quiescence, fresh Publisher proof, cross-store transition journal, Guest verification and rollback.
