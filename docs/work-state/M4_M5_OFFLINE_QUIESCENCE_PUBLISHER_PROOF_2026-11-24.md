# P1 M4→M5: offline Editor quiescence fence + fresh Publisher private-key proof — 2026-11-24

**Integration:** Draft PR #620. **Release/field status remains `FIELD_BLOCKED`.** This is a tested internal foundation for a later Owner-authorized, cross-store transition; it is **not** an Editor pause/ACK protocol, a new WebSocket endpoint, a Host/Guest switch or approval to enable live M5 updates.

## Risk / constraints

An M4→M5 transition must not assume that a signed new Baseline file is a live Publisher's private-key possession proof, or that all realtime editing has stopped while an async signed source admission is still executing. Even a valid M5 signed Descriptor can be replayed after losing a Publisher key. Conversely, an unsafe implementation that locks only Hierarchy writes but permits Collider/Component joins or new Editor Hello frames could silently corrupt or fork revisions.

For now, **only an entirely unoccupied signed Project** may enter offline quiescence. It requires no connected Project clients (Editor or Seed), no Session members, no live lock leases, no pending async source admission, a stable approved M4 signed Descriptor, no concurrent transition review, and a ready healthy durable Coordinator. A still-connected Editor is *not* presumed to have paused. Any future multi-Editor transition must implement explicit Editor write-pause/ACK/timeout, reconnect fencing and complete Guest Active handoff first.

## Implemented

- `server/src/project-transition-quiescence.mjs`: in-memory per-Project barrier with reference-counted async source admission leases. A freeze only starts after all local preconditions are empty. A frozen Project refuses new source admissions, prevents new Editor Hello sessions and all existing non-ping WebSocket commands by default, including Hierarchy/Transform, locks, Collider/Component, Publisher/Seed announcements and future unknown commands. Unrelated Projects remain operational. An unforgeable **object-identity** ticket pins the approved old UUID, Manifest/Descriptor, revision and Owner key and is retired by explicit release or server shutdown.
- `server/src/teamforge-server.mjs`: tracks async M4 signed-source checks and Collider join admission until each returned Promise settles, preventing a successful offline freeze while an earlier admission is still pending. Internal `tryBeginOfflineProjectFreeze` and `releaseOfflineProjectFreeze` have **no corresponding WebSocket operation** and must not be treated as remote-authenticated actions. All previous traffic stays unchanged unless a trusted in-process controller explicitly obtains a freeze.
- `server/src/project-transition-publisher-proof.mjs`: uses the **existing** Ed25519 signed Baseline and Owner-to-Publisher delegation verification, then issues a fresh random 32-byte, 30-second, domain-separated challenge over exact previous/new UUID, revision, Manifest/Descriptor hashes, Publisher key, challenge ID and expiry. Only the currently authorized Publisher private key can sign it. A wrong signature, expired/replayed nonce or cross-Project key fails. A challenge is consumed on the first verification attempt; stale nonces can expire and be replaced. A successful receipt is accepted only through exact **in-process object identity** with the original freeze, candidate hash and expiry; copying the JSON result cannot forge usable authority. Releasing the freeze revokes any pending challenge or receipt.
- The server object exposes internal `issueOfflinePublisherChallenge`, `verifyOfflinePublisherChallenge`, `isOfflinePublisherReceiptCurrent` only to its owning Node process. **Neither a valid Publisher proof nor a freeze authorizes SQLite writes or a Host pointer change.** A future signed transition controller must separately check immutable candidate contents, Editor and Guest states, SQLite transaction/journal, explicit Owner approval and rollback conditions.
- The existing transport/Unity wire protocol is unchanged. The development source remains release-blocked until actual Windows 2-PC Unity tests and cross-store crash/rollback finalization.

## Negative and user-work preservation evidence

- In-memory tests reject occupied Editors, members, locks, unsigned/fake baselines, malformed Project identities, simultaneous/pending async source validations, duplicate freezes, forged/copy tickets and replayed/expired Publisher signatures. Separate Projects retain independent admissions.
- Real durable WebSocket integration: an accepted native Cube and Collider creation is persisted; while the Editor is connected, offline freeze refuses. After server-observed disconnect and no active locks, the Project freezes. New Editor Hello is rejected, while a second unrelated Project's heartbeat remains live. A legitimate new signed M5 candidate requires a fresh signature from the current Owner/Publisher. After explicit release, the copied proof no longer validates; the Editor reconnects with the **same durable lineage**, reconstructs the previous native Cube/Collider and successfully commits a further Collider property edit at the previous revision + 1.
- Final Ubuntu Mini PC/Node 24 evidence: Server **486 PASS / 0 FAIL**, Project Peer **651 PASS / 0 FAIL / 6 environment SKIP** (657 total), cross-Phase **150 PASS / 0 FAIL**; Host/Seed smoke and `npm --prefix server run check`, engineering/docs/workflow/public-source validation all PASS. Test-suite totals overlap. Exact new-commit GitHub CI remains independent.
- This is in-process quiescence only; it is lost on process restart. Durable SQLite M4 backups and unresolved transition journals, implemented separately, remain the crash-safe recovery authority. The freeze does not persist an Edit-paused ACK or guarantee that local Unity filesystem activity has stopped.

## Remaining work / release gates

The next P1 requirements are an explicit Editor-side pause request, positive and negative ACKs for **each** active Editor, timeout/connection loss handling, freeze-bound signed Publisher possession proof over the live protocol, exact candidate source/scene and asset verification under a stable Host source state, SQLite/Host promotion intent, retained Guest Active rebind and optional rollback timeline. This checkpoint never enables a live commit. Source checks and CI for the exact new commit must be recorded independently; do not infer physical Windows validation, real power-cut recovery or release ZIP readiness.
