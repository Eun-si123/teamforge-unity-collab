# M5 — Unity native asset imports invalidate signed Project review previews

**Development checkpoint · Draft PR · Source only · Not field-validated**

## Problem and observed implementation

TeamForge's existing Host UI already has a read-only saved-source checkpoint comparison against the signed Publisher-approved Baseline. It does **not** activate a new revision or magically synchronize third-party FBX/Prefab/material data as M1–M3 live messages. That is correct: the Node Coordinator requires an authenticated Project checkpoint transition while retained M2/M4 component edits exist. However, the Editor previously kept showing a successful or "no changes" preview after a user imported, removed or moved an Asset or saved a Scene. A comparison from before an import cannot tell the user whether marketplace content is in the currently approved Baseline.

## Narrow implementation

- Native Unity `AssetPostprocessor.OnPostprocessAllAssets` observes imported, deleted, renamed/moved **Assets/** and embedded **Packages/** content using **path-only notifications**. `EditorSceneManager.sceneSaved` handles saved Scene edits. No filesystem polling, network request, import interception, custom asset format, automatic file transfer, or runtime protocol is added. Paths are never logged/copied to public telemetry, and non-project/unsafe paths do not initiate a preview refresh.
- Only an actual Host Ready session with a previously verified pinned M5 checkpoint preview context may mark local source changes. An idle, Guest, stopping or disconnected session is unaffected. A single delayed UI refresh coalesces entire import batches, so Unity importing many model/material/texture files does not trigger repeated work.
- On source change, immediately discard the old `Review` and increment a local generation serial; a preview worker started before the change is no longer allowed to publish its result. When the previous read-only preview is still running, request its cancellation **after** the Asset import callback returns. The old worker's finalizer cannot clear a new session's cancellation token. Neither the import nor cancellation changes the signed Baseline, sends a command to another Editor, or stops the Host.
- The existing Host "Review saved changes" control shows a localized warning: imported Prefab/model/texture/package and Scene edits are **not** yet shared to peers. Unsaved Scene content is also called out. After a fresh successful preview, the hint can clear, but any real changed-file summary remains explicitly labeled **NOT published**.

## Safety boundaries

The existing M5 checkpoint preview remains **read-only** with the same signed `projectUuid`, revision, SHA-256 digest and bounded output/path validation. A local event is never authority to distribute untrusted marketplace content. The UI intentionally does not offer an unaudited "Publish Now" during a live durable Collider Session; the Coordinator currently blocks uncheckpointed baseline swaps. Existing signed Project Peer transfer/review is still required for external assets. This change is visibility and stale-result correctness only, **not external Prefab live sync**.

## Verification scope

Authored Unity EditMode tests in `TeamForgeUxTests`: `UnityNativeAssetNotificationsDetectImportedMovedDeletedProjectFilesOnly` covers relevant import/delete/move and embedded Package paths while excluding Library/Temp, absolute paths and path traversal; `AssetImportInvalidatesOnlyCurrentHostCheckpointReviewWithoutPublishing` exercises a synthetic Ready Host with an old preview, verifies that a local import discards that preview, invalidates a captured generation, preserves the Host state and does not publish. The test restores the static Host state and does not start a Coordinator or write user files.

Local lightweight source/documentation/engineering checks are run separately. **No real Unity Editor test, marketplace package import, publish, two-Windows-PC transfer or signed Guest activation is claimed by this checkpoint**. The release remains `FIELD_BLOCKED`; the later batched field plan should import an Asset Store/FBX Prefab, save the Scene, verify the stale review is removed, verify a fresh signed diff includes `.meta` dependencies, and test the separately approved Project update/Guest activation without overwriting unsent M4 edits.

## Unity GUID companion verification (follow-up)

The M5 preview now also checks whether **added or modified `Assets/` files** have matching `.meta` companions **in the already verified snapshot Manifest**. It also catches a removed `.meta` whose corresponding Asset remains, without warning for unrelated unchanged legacy fixture files. These warnings are **not** a new authorization to publish. Unity references assets by GUID; byte-perfect FBX/Prefab transfer without its original `.meta` may change Unity GUIDs or break prefab/material references on another PC. Generating a fresh `.meta` in TeamForge would be unsafe, so the Host UI instead shows a bounded count and path preview, asks for original metadata restoration, and continues to require the existing signed Project update workflow.

The Node preview contract adds `missingAssetMetaCount`, `missingAssetMetaPreview` and `missingAssetMetaTruncated`. All paths remain sanitized, limited to 20 entries of up to 640 UTF-8 bytes, with exact count preserved when the preview truncates. The Unity decoder validates the new count, bounded path list and truncation rule; it refuses contradictory or unsafe responses. A direct Node focused suite `node --test project-peer/test/host-checkpoint-preview.test.mjs` **passed 7/7**, including a real synthetic FBX/Prefab import with and without metadata and proof that read-only comparison changed no files. New Unity decoder negative cases were authored but **not yet run in Unity**. This does not establish real two-PC workflow support or durable live-Baseline transition readiness.

## M4 → M5 signed-source transition preflight (follow-up)

**Why the live version cannot simply be incremented:** The M4 durable Coordinator saves a signed Project descriptor alongside the Collider owner/Scene source pin, admitted Component identities, accepted property/Hierarchy/Transform values and an exact session-revision journal. A new signed M5 Manifest can change file paths, Unity GUIDs, scene bytes or compiled component definitions. Mutating only the published revision would make an old M4 checkpoint unrecoverable or bind prior edits to a different source. The current `durable_checkpoint_required` and `component_checkpoint_required` server gates must remain in place until a correctly ordered durable transition is implemented.

The existing **read-only Host checkpoint comparison**, which already loads the previously approved signed Manifest and constructs the candidate Manifest without publishing, now returns a bounded `transition` report. The `previewRetainedM4SourceChanges` pure classifier compares those two verified Manifest path sets and reports whether the previously approved Scene `.unity` and `.meta` paths remain untouched, including rejection of baseline Scenes that had no original `.meta`. It identifies changed or removed prior `.meta` companions, executable code / script assemblies, `Packages/` and `ProjectSettings/` sources, and changes to previously approved Prefabs. Added marketplace assets with original new `.meta` and unchanged previous Scene may be classified `source_inputs_unchanged`, **but this proves only a necessary source-file precondition, not live M4 compatibility or authorization**. Any ambiguous original Scene, script, Prefab, metadata or Package change yields `source_reconciliation_required` with per-category counts and at most 12 short display paths; exact conflict counts are retained even when paths are truncated. A no-change preview uses `no_saved_changes`.

The Unity Host panel consumes this nested advisory result in English/Korean, shows categorized conflict counts, displays affected relative paths, and explicitly states that an M4 durable checkpoint plus peer Project refresh are still necessary **even when the source files appear unchanged**. The Unity decoder validates exact status vocabulary, bounded counts and paths, and rejects a forged 'unchanged' status combined with nonzero conflict counts. The asynchronous UI publishes its successful `Review` and `TransitionPreview` *together only for the same pinned source generation*; parsing test responses cannot mutate live UI state, and Asset imports clear both stale records.

**Executed evidence:** `node --test project-peer/test/host-checkpoint-preview.test.mjs` **9/9 passed**, covering real temporary signed-project manifests with imported FBX plus original metadata; each of Scene content modification, deleted original Scene `.meta`, changed prior Prefab, added C# script and Package manifest modification; read-only source filesystem identity preservation; old Scene lacking `.meta`; and bounded conflict lists. The existing real WebSocket M4 durable restart scenario was extended with a correctly signed next-revision Owner descriptor sent **after** accepted Transform and Collider edits: the server returned `durable_checkpoint_required`, preserved the current signed source, Component values and revision, and the original persisted M4 values survived Coordinator shutdown/restart. Focused run `node --test --test-name-pattern='M4 signed WebSocket edits survive' server/test/primitive-collaboration.test.mjs` **1/1 passed**. Unity response-decoder regression cases are authored but not yet executed; two-Windows-Editor field validation remains deferred.

**Not implemented:** This does not acquire an M4 write-freeze, acknowledge readiness of every collaborating Editor, persist a new signed Project pin atomically with the retained M4 history, install a new Coordinator Scene Component epoch, update a Seed, perform a Guest verified-Active refresh or prove previous Assets/.meta GUID relationships after actual Unity import. Those separate protected transitions remain **mandatory** before turning this diagnostic into a live-project upgrade path. Never infer successful cross-client update from `source_inputs_unchanged` or weaken the current server rejection to force progress. Release remains `FIELD_BLOCKED`.
