## 2026-11-22 follow-up — cross-Phase M4/M5 completeness and imported Asset GUID evidence

### Confirmed cross-Phase gap 1: M4 no-Collider Sessions were invisible to M5 source preview

Previous `project_baseline_transition_preview` watched `components.ledgers` and its Session revisions, but omitted independent M4 realtime Sessions containing only Transform/Hierarchy state. During an asynchronous signed-Manifest read, a second durable Session could edit, reconnect, change its lease owner, or replace its checkpoint cursor without invalidating a seemingly current candidate review. This is a **confirmed completeness gap in an advisory path**; it did not bypass the separate `durable_checkpoint_required` publication guard, and no accepted edit loss was demonstrated.

The Coordinator now snapshots **every** realtime Session belonging to the exact Project, including object/generation identity, revision, durable epoch, durable lineage, registered connection identities, and lease ownership/expiry. It also checks the Project's durable checkpoint cursors (exact Project UUID, Session key, revision consistency) and retained Collider ledger pins/epochs. The same snapshot is reacquired after asynchronous Manifest and pointer reads; any addition, retirement, reconnection, lease, revision, checkpoint or Component source drift invalidates the preview as `project_transition_stale`. Other Project sessions do not create false conflicts. Response and Project Peer client validate bounded counts `retainedRealtimeSessions`, `retainedDurableCheckpoints`, and `retainedComponentSessions` for correlation. These counts are **not** a quiescence ACK, a write freeze or an M4→M5 commit authorization.

### Confirmed source input blind spot 2: identical copied Unity .meta files

The prior `missingAssetMetaCount` checked presence only; newly imported FBX/Prefab could copy an existing Asset's entire `.meta` bytes and thereby reuse its Unity GUID. The shared, transport-free signed-Manifest source classifier now detects byte-identical `.meta` SHA-256 hashes for distinct `Assets/` companions, restricted to the newly touched Assets/metadata so an untouched old baseline remains a no-op. These become `source_reconciliation_required` blockers and the Host and server report `identicalMetaCount`; the bilingual Unity UI shows this count and affected short relative paths from the existing bounded conflict preview. Project Peer rejects contradictory wire approval/count responses. This is **not** exhaustive GUID uniqueness verification: differing `.meta` bytes can still contain the same GUID, and Source `source_inputs_unchanged` remains non-authorizing even without duplicates.

## 2026-11-22 late follow-up — staged signed Asset GUID content audit (no publication)

**Confirmed gap beyond identical-byte `.meta` checks:** two distinct `.meta` files can contain the same Unity GUID with different legitimate text or import settings. The previous hash-only duplicate check did not detect this. Source metadata presence alone also does not prove that the signed `.meta` chunks exist or match their declared file hashes.

The M5 Coordinator read-only `project_baseline_transition_preview` now loads only `Assets/` and embedded `Packages/` `.meta` contents from the exact **stored, signed candidate Manifest**, using the existing verified ChunkStore reads. The audit hashes every reconstructed metadata file against its signed Manifest `fileHash` and extracts a single 32-character nonzero Unity GUID. Newly touched assets with different-byte duplicated GUIDs, invalid metadata or duplicate GUIDs inherited from package resources are added to the conflict list. Older untouched metadata defects are not newly attributed to an unrelated import. The reply exposes `duplicateGuidCount`, `invalidGuidCount`, `auditedMetadataFiles` and `candidateMetadataAuditStatus` (`verified` / `resource_limit`) with **counts only**; it never returns raw source bytes, stored chunk paths or secrets. The Project Peer wire decoder rejects inconsistent counts, unsupported statuses, any fabricated commit-permitted response and any claim of complete auditing after a resource limit.

**Fail-closed and bounded:** Each all-or-nothing read-only audit caps individual metadata at 2 MiB, aggregate metadata at 32 MiB, up to 8,192 metadata files and 8,192 chunks. If the candidate exceeds those limits the Coordinator **does not read partial metadata** and returns `candidateMetadataAuditStatus:resource_limit`, never `verified`; callers must not interpret zero observed conflicts as a uniqueness proof. Corrupt or missing exact signed chunks return a sanitized source-unavailable error with no apparently verified report. A closed WebSocket cancels the scan and clears the per-Project busy slot. The audit does **not** scan arbitrary source paths or the large FBX/texture body chunks, cannot guarantee staged files remain on disk afterward, and does **not** replace an eventual complete Asset GUID/contents verification during atomic M4→M5 promotion and Guest activation. `candidateStoredChunksVerified` and `commitPermitted` **remain false** on every accepted reply, and the existing `durable_checkpoint_required` fence is intact.

## 2026-11-23 — atomic M4 durable multi-Session checkpoint storage primitive (Draft only)

**Confirmed implementation gap:** The M4 SQLite owner previously exposed only `commit()` for individual Session rows. Applying a new signed Project baseline to two retained Sessions through separate calls could leave half of the Session group on old M4 source/epoch if storage filled or the process crashed between writes. That is unacceptable even if a higher-level Coordinator would correctly refuse a prematurely changed Publisher.

The isolated integrated Draft now adds **internal** `store.transitionProjectCheckpoints(...)` to the existing schema-v1 durable SQLite owner. It accepts an exact list of every persisted Session for one Project, each with a compare-and-swap (CAS) of the **previous epoch, revision and checksum**; it checks the complete persisted Session set for omissions, extra Sessions, duplicate/wrong Project UUIDs, and races. The target Session checkpoints must share one next-revision descriptor and Publisher publication attribution, use fresh epochs, preserve **the exact realtime Transform/Hierarchy values, retained Collider property/structure values, lineage and revision**, and repin the signed Collider source fields **without silently changing admitted Scene identities or source bytes**. All checkpoint rows are updated under a **single SQLite `BEGIN IMMEDIATE` / `COMMIT`**, with rollback on any validation/storage exception. Old operation receipts remain under their previous epochs; they are not replayed as new-epoch edits. No schema migration or destructive database reset is introduced.

**Evidence boundary (critical):** This is the first atomic **SQLite-only** primitive, not the full cross-subsystem M4→M5 transaction. It is intentionally **not wired to any WebSocket command or runtime Publisher operation**. A later authenticated Coordinator workflow must still obtain Editor write quiescence and all needed acknowledgements, verify Owner/Publisher possession and the complete candidate again, coordinate the Project Peer on-disk approved pointer and Seed/Guest Active separately with a persistent crash-recovery journal, and make the new signed Scene/Component epoch consistent before invoking this primitive. SQLite cannot atomically commit an external Project pointer or Guest disk state; using this function alone would risk a restart-unavailable source mismatch. Direct new-Baseline publication remains blocked by `durable_checkpoint_required`, while `commitPermitted` remains false in the preview. Keep the immutable r11 release and physical two-Windows-Editor evidence strictly unchanged (`FIELD_BLOCKED`).

**Focused tests:** `server/test/durable-session-store.test.mjs` now covers a two-Session Project (signed Collider + independent Hierarchy-only Session), unrelated Project isolation, accepted edit/receipt and exact lineage survival across database close/reopen, duplicate/omitted/foreign Sessions, stale epoch/revision/checksum, changed Collider/Transform/Hierarchy/source pin, mismatched future publication, **actual `SQLITE_FULL` rollback with unchanged old epochs**, and actual subprocess `SIGKILL` after batch commit and before reply (both new Session records recover together). These cases are now part of the `test:crossphase-node` lane; full crossphase/Server results are separately recorded once run.
