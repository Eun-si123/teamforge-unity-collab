# M4 recovery atomicity + M5 historic-epoch guard — 2026-11-24

**Scope:** M4 persisted-session crash recovery and a defensive guard in the *internal*, non-published M4→M5 SQLite batch. Integrated Draft #620, source-only. This note is a dated checkpoint, **not** the current release/feature-status authority; see [`../STATUS.md`](../STATUS.md) and [`../PRODUCT_DECISIONS_2026-11-23.md`](../PRODUCT_DECISIONS_2026-11-23.md).

## Problem and bounded change

Prior runtime startup restored and validated all durable M4 Sessions, then committed fresh authority epochs **one Session at a time**. A process crash, storage failure or interruption between commits could leave a durable database containing a mixture of newly rotated and old epochs even though no restored Session was intentionally exposed before its own row had committed. The last accepted Project/Transform/Hierarchy/Collider data remained durable, but recovery was needlessly partial and could require another restart to converge. The user has explicitly prioritized work preservation and reliable restart behavior.

The existing schema-v1 `openDurableSessionStore` now provides `rotateRecoveredEpochs({sessions})`. It takes a complete, bounded list of previously verified Session checkpoints, validates scope, epoch, revision, checksum, exact membership **across all Projects**, uniqueness of all new epochs, and absence of a reused old epoch with historical accepted-operation receipts. Under a single SQLite `BEGIN IMMEDIATE`, every checkpoint's checksum is recomputed for its fresh epoch while **the exact previous serialized checkpoint JSON, revision, signed Project source, lineage and operation journal are left untouched**. CAS is checked on each row and rollback is required on any error. Fresh epochs never inherit stale journal outcomes.

`DurableSessionRuntime.restore()` still fully validates signed Projects and materializes restored Scene/Collider state before the startup transaction, but now makes **one** call to rotate all epochs and only then publishes the recovered authority Sessions to in-memory maps. The Coordinator must fail startup if the store rejects rotation; no partial authorizing service is brought online. A preexisting empty DB is supported. There is no new schema version, no SQLite reset, no public protocol field and no downgrade in fail-closed gates.

For the separate, **future-only** `transitionProjectCheckpoints()` M4→M5 storage batch, an additional guard rejects proposed next epochs that collide with past accepted-operation receipts for the same Session. It prevents a delayed operation in an old epoch from being confused with newly migrated authority. This still **does not** authorize a running signed Baseline transition or write to the Project published pointer.

## Boundaries and next safe product work

This batch is a **recovery hardening step** supporting P1, **not completion of M4→M5 automatic version switching**. The latter still needs Editor quiescence and ACKs, Publisher fresh key-possession proof, verified signed candidate and immutable source pin, a crash-recoverable journal spanning SQLite and the external approved Project pointer, Seed rebind and independently verified Guest Active refresh with rollback. Current preview continues to report `commitPermitted:false`; baseline publish stays blocked by `durable_checkpoint_required`. Unity Editor local execution, physical Windows two-PC runs, exact new ZIP identity, externally imported Prefab live synchronization and Release promotion are NOT RUN / NOT IMPLEMENTED.
