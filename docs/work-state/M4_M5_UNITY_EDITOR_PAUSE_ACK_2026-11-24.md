# P1 M4→M5: Unity Editor-side pause ACK + native-change invalidation — 2026-11-24

**Branch:** agent/teamforge/full-native-project-flow-20261122, Draft PR #620. **Product release status remains `FIELD_BLOCKED`.** This is an opt-in Editor implementation for the *existing server-side* online pause preparation protocol. It neither switches the signed Host baseline nor authorizes a Guest Active/SQLite M5 transition.

## Behavior

- The Editor now offers `supportsProjectEditPause` in a new subclass of Hello, preserving legacy `HelloMessage`, `PrimitiveTemplateHelloMessage` and Collider Hello DTOs. The Coordinator negotiates `projectEditPauseEnabled` only for a durable Editor. Older Coordinators that do not negotiate this feature continue normal M4 editing; unsolicited pause frames are refused.
- Before replying to a `project_edit_pause_request`, Unity checks the exact current signed Coordinator baseline (Project UUID, Manifest/Descriptor hashes, revision), authenticated connection and durable Session epoch/lineage/revision, deadline and a fresh pause UUID. The request must match this Editor's actual authoritative cursor.
- The Editor **returns `busy` rather than claiming to be paused** if any Scene is dirty/unsaved/unloaded, Unity is importing/compiling/entering Play Mode, native remote apply is underway, outbound application sends or queued main-thread callbacks remain unresolved, Hierarchy snapshots/seeds/operations are pending, Transform lock/update/recovery conflicts remain, Collider property/structure work is pending or recovery is unresolved, or the signed Project registry is not ready. No automatic Scene save, Asset replacement, Undo, discard or Project switch occurs.
- Only after these checks pass does the Editor install a per-connection outbound barrier and send `status=ready` over the existing authenticated WebSocket. While paused, **all** application writes (Hierarchy/Transform/Collider/Presence/Project, new operations and unknown future message types) are blocked locally; only ping and the exact pause ACK may go out. The server separately rejects inbound writes, new Editor connections and any ACK from a different durable Session.
- Unity's ordinary GameObject/Inspector changes, object change stream, Scene dirty/save/open/close/active switch, Undo/postprocess events, Asset database project changes and Play Mode transitions invalidate a previously acknowledged pause. During `Update`, a changed local state/cursor/expiry or any unacknowledged send triggers a safe WebSocket disconnect, which causes the server's all-Editor pause to abort. The original M4 local changes, Unity Scene objects, Undo history and existing TeamForge recovery records are **not deleted or reset** by the pause gate. The ordinary guarded M4 reconnect/reconciliation flow remains responsible for resuming work.
- An exact matching `project_edit_pause_cancelled` removes the local barrier and resumes ordinary M4 traffic. Stale cancellations cannot unlock a newer pause. `project_edit_pause_acknowledged` never authorizes a commit; a malicious response claiming `commitPermitted=true` ends the connection without switching the Project.
- UI diagnostics include whether the pause capability was negotiated and whether outgoing Project edits are currently paused. No manual Shared Object creation workflow was introduced.

## Remaining gates

This prepares a safe **transport pause ACK**, not an absolute attestation of every Asset/Prefab byte on disk. The Editor does not freeze external disk writers, all third-party editor scripts, OS file changes or in-flight Guest Active transfers. A positive ACK never implies that the complete local Project source is immutable or that a save/rollback is authorized. Before any real M4→M5 commit, implement bounded exact-source verification for all Assets and Scenes, save/dirty generation capture, locally persisted fallback recovery, a fresh Publisher signing challenge over the live transition, version-wide Host↔SQLite↔Guest upgrade/rollback with crash recovery, and two-PC Windows Unity tests. All claimed states must be verified independently.
