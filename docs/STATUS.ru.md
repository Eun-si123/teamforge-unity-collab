## Исходники и опубликованный пакет

Исходные исправления WP5.1 для #67, #68/#74, #69, #70 и #71 объединены через PR #81. r5 выпущен из указанного коммита и включает их, а также интеграцию Launcher **Save support bundle**, добавленную после r4.

2026-08-31 именно r5 проверили на двух физических ПК Windows: повторное подключение сохранённого Guest, новый поздний Guest со снимком Transform, многократное прерывание приёма/возобновление, передача управления через execution alias для длинных/глубоких путей и восстановление после защищённого конфликта устаревшего соперничества за lock. После необходимого разрешения брандмауэра физически проверили Host Stop/Start с повторной привязкой Seed TCP `5091` и настоящий перенос Project к Guest.

Эти сценарии больше не ждут первого физического повторного теста r5. Это не включает последующие изменения в r5 и не делает продукт общедоступной для установки альфой. Утверждения о пакете относятся к r5 и результатам 2026-08-31; r5 не эквивалентен `main` по байтам или поведению. Не объявляйте закрытые сценарии снова ожидающими лишь из-за старых текстов. Если распространять `main`, нужен новый неизменяемый артефакт с проверкой добавленного после r5 поведения именно на нём.

## Усиления после r5, отсутствующие в r5

- Настройка Windows LAN брандмауэра может после явного согласия пользователя и UAC создавать узкие входящие правила Coordinator/Seed только для профиля Private и LocalSubnet, с согласованием/очисткой собственных правил TeamForge. Физический r5 требовал ручного разрешения; новый путь нуждается в физических доказательствах точного пакета.
- Занятый/недоступный предпочтительный или стандартный порт Seed, включая `EACCES` при Windows bind: Host повторяет попытку один раз с портом, назначенным ОС, и объявляет выбранную конечную точку. Есть автоматические тесты Windows Project Peer, но поведение новее r5.
- Последовательное создание идентичности Project и восстановление после аварии Windows через принадлежащую ОС активную named-pipe блокировку и постоянный барьер совместимости для старых записывающих процессов. Наборы crash/concurrency Windows Node 22/24 прошли; опубликованного пакета с этим изменением и точными физическими доказательствами ещё нет.
- Очистка при отказе Coordinator, усиление отмены/сроков HTTP, контекст диагностики Host, журналы ролей клиентов WebSocket и более ясное различие приглашений Launcher и кодов `TF1`.

Это факты об исходниках/автоматизации, не о поведении пакета r5. Восстановление устаревших блокировок идентичности Linux/macOS также вне этого изменения для Windows.

## Два физических ПК

Базовый сценарий 2026-08-22: Host → подписанное приглашение → новый Guest → аутентификация → прямой перенос → доверие Publisher → проверенный Active → Unity realtime; Presence и двунаправленный Transform; обычное соперничество lock; создание/переименование/смена родителя/порядок соседей/удаление в одной Scene. Выход/повторное открытие Guest без сохранения восстанавливали Hierarchy/Transform/Lock из ещё работающей сессии. Обрыв TCP Coordinator → retry → автоматическое подключение без рестарта Unity.

2026-08-31 точная пара ZIP/SHA r5 закрыла указанные целевые сценарии на двух физических Windows ПК. Seed `5091` Stop/Start и настоящий LAN перенос тоже прошли; начальное разрешение брандмауэра тогда оставалось ручным.

## Границы доказательств

Результат доказывает лишь выполненное. CI исходников не доказывает корректность ZIP. Автоматизация Unity не воспроизводит каждый порядок ввода SceneView, состояние процессов Windows, LAN/брандмауэра или тайминг второго ПК. Одномашинные тесты делят ОС, сетевой стек, временную среду и оборудование. r5 не доказывает более поздний `main`. Версия не равна идентичности байтов: нужны точное имя артефакта и SHA-256. Закрытый баг не даёт последующим изменениям подсистемы автоматических пакетных/полевых доказательств. Исторические записи верны для своих снимков, но не заменяют текущий STATUS.

## Оставшиеся условия выпуска

До представления продукта как общедоступной для установки альфы:

1. Сохранять физические закрытия r5 #67/#68/#69/#71/#74 как завершённые.
2. При распространении `main` выпустить новый неизменяемый кандидат.
3. На точном заменяющем артефакте проверить начальную настройку брандмауэра, узкую область/жизненный цикл правил, fallback занятого/недоступного порта, реальную достижимость объявленного Seed, Host Stop/Start и перенос нового Guest.
4. Там же проверить Windows-восстановление идентичности после потери процесса, безопасный перезапуск и сохранение fail-closed для неоднозначных/конфликтующих идентичностей.
5. Выполнить smoke заново распакованный Host → новый Guest → realtime на заменяющем пакете, не наследуя r5 доказательства по предположению.
6. Сохранить точные имя/SHA/идентичность источника и только реально выполненные сценарии.
7. Продолжать инструкции установки/обновления/удаления и получить тесты/проверки от людей помимо создателя до широких заявлений о надёжности.

Перезапуск серверного процесса сейчас — **разрыв/fail-closed/восстановление новой сессией**, не тест постоянного хранения: устойчивое восстановление authority/session после рестарта не реализовано.
