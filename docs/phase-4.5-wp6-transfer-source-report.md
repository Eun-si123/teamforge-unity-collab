Implementation consequences:

- Node Fetch is Undici-based and a response body must be consumed or cancelled. Direct HTTP continues to consume bounded bodies with async iteration; the declared-oversize branch now awaits body cancellation before rejecting.
- Stream backpressure is an adapter/host concern. The existing direct server write/drain behavior and its abort tests remain unchanged. The client continues pull-based bounded consumption and does not expose a raw HTTP stream to Transfer Core.
- HTTP status, content type, `Content-Length`, `Retry-After` and the existing millisecond extension are transport metadata. They remain inside `DirectTransferClient` and are translated to normalized retry/error information.
- RFC 9110 defines HTTP metadata semantics, but HTTP transport success is not Project content trust. Existing Manifest identity, expected Chunk size and SHA-256 verification remain authoritative.
- RFC 9530 explains HTTP digest fields but WP6 does not add one: doing so would change the existing Project Transfer v1 route/headers. TeamForge continues its application-level Manifest/Chunk SHA-256 checks.
- `crypto.createHash('sha256')`, verified Chunk reuse, immutable Active directories, and atomic pointer activation remain unchanged. `fs/promises` concurrency cautions support retaining the existing explicit locks/non-overwriting writes rather than adding parallel mutable registry writes.
- The existing `ws` Coordinator path is not a payload transport and was not edited.

## New Project Transfer Source contract

`PROJECT_TRANSFER_SOURCE_CONTRACT` is deliberately structural and versioned `1`. A source provides exactly these operations:

| Operation | Result boundary |
| --- | --- |
| `descriptor()` | Signed Project Baseline Descriptor candidate; existing validation remains in discovery/Core. |
| `manifest()` | Canonical Project Transfer v1 Manifest candidate; existing hash/schema/revision validation remains in discovery/Core. |
| `inventory()` | Project/Manifest-bound list of available content hashes; existing foreign/invalid hash rejection remains in Core. |
| `chunk(hash, expectedSize)` | Bytes for one content-addressed Chunk; the real adapter enforces request bounds, expected size and SHA-256, and Core performs its existing second verification before storage. |

This is a JavaScript structural port, not a new abstract base class, dependency-injection container, route registry, or protocol version. `assertProjectTransferSource` performs the minimum runtime shape check.

## Direct HTTP adapter responsibility

`DirectTransferClient` remains the first and only real adapter. It owns:

- endpoint validation and exact Project Transfer v1 paths;
- Bearer token and Project UUID/Manifest Hash/Session ID request headers;
- Fetch timeout/abort and bounded body consumption/cancellation;
- HTTP status and transient status classification;
- standard `Retry-After` plus the existing `X-TeamForge-Retry-After-Ms` parsing and 60-second cap;
- safe server/network diagnostics without raw response bodies or credentials;
- JSON/octet-stream content-type validation;
- Chunk request bounds, expected-size verification and SHA-256 verification.

No new transfer route, source discovery mechanism, dependency or user setting was added.

## Transfer Core / adapter error boundary

The adapter creates the same public `TeamForgePeerError` codes and legacy `details` fields as before, and additionally attaches non-enumerable normalized source information. `transferSourceErrorInfo` also accepts the pre-WP6 legacy error shape so existing fake/characterization sources remain valid.

`SwarmDownloader` consumes only:

- `errorKind`;
- `retryable`;
- bounded `retryAfterMilliseconds`;
- a sanitized diagnostic record copied to the existing `httpStatus`, `networkCode`, and `serverErrorCode` output fields.

It does not inspect a Fetch `Response`, HTTP status, HTTP header, or raw body. Retryable 408/425/429/500/502/503/504, timeout/network classification, exponential backoff/jitter, `Retry-After` override, failover and diagnostic output remain covered by the original tests. The historical diagnostic field names are retained for compatibility but are not used by Core to interpret HTTP semantics.

## Stable backend registration

`PROJECT_PEER_STABLE_BACKEND` records:

- backend ID `project-peer`;
- Project Transfer Protocol version `1`;
- `ProjectPeerEngine` as the engine;
- `DirectTransferClient` as the sole real source adapter.

This is an additive, immutable registration surface. CLI commands/options, launch settings, Invite/Descriptor schemas, Coordinator messages, direct server routes, Seed advertisements and payload topology are unchanged.

## Behavior parity

- Manifest construction, canonicalization and validation sources were not edited.
- Chunk SHA-256/expected-size checks remain in the Direct adapter and in Core before `ChunkStore.put`.
- Resume still reuses only `store.has(hash, size, true)` verified content.
- Swarm selection, inventory filtering, concurrency, pacing, retry/backoff/failover, rate-limit response meaning and partial-Seed announcements are unchanged.
- Staging/trust review/immutable Active revision/atomic Current pointer code was not edited.
- Project Transfer v1, Realtime Protocol v1, Invite/Descriptor/Manifest schemas and error codes were not changed.
- Project payload continues to move directly between `project-peer` processes and never through the TeamForge Server.

## Risks and ambiguities

- The source contract is runtime structural JavaScript. It intentionally does not introduce TypeScript, an abstract class hierarchy, an interface package or dynamic adapter discovery.
- The adapter buffers each response after bounded pull consumption. The existing JSON/Chunk caps limit memory, but a future streaming-to-store design would be a separate behavior/performance work package.
- HTTP-date `Retry-After` necessarily uses wall-clock time; the result remains capped to 60 seconds. Existing retry classification and jitter tests freeze current behavior.
- Legacy diagnostic keys include `httpStatus` for operational compatibility. Core copies normalized diagnostics but does not make HTTP decisions from that field.
- Direct HTTP can be plaintext on trusted LAN/VPN paths as before. TLS termination and network access policy remain deployment responsibilities.
- Fake source is a test double only, not a second production route or adapter.
- Unity EditMode validates compilation/static editor behavior, but WP6 did not execute a new A/B/C multi-process manual transfer session.
