# Как работает TeamForge

Страница объясняет, **что происходит при запуске Host, присоединении, переносе проекта, правке Scene, разрыве связи и восстановлении после ошибки**. Это последовательное объяснение, не полная спецификация протокола или карта файлов исходников.

Возможности/блокеры: [Состояние](STATUS.ru.md); топология/границы доверия: [architecture](architecture.md); файлы: [CODEMAP](../CODEMAP.md); причины решений: [architecture-decisions](architecture-decisions.md). Непереведённые подробности остаются на английском; [English](HOW_IT_WORKS.md) определяет смысл.

## Модель за 60 секунд

Два намеренно разделённых пути данных:

- Host/Guest Unity Editor посылают realtime операции по WebSocket в Session Authority Server.
- Host Unity использует Host Project Peer/Seed, Guest Launcher — Guest Project Peer. Данные проекта идут напрямую между Peer по HTTP; Guest Peer передаёт проверенный Active в Guest Unity.
- Server координирует подписанные метаданные с обоими Peer, но не становится ретранслятором файлов проекта.
- Guest открывает контент только после проверок доверия, целостности, активации и передачи управления Unity.

Большие переносы отделены от чувствительного к задержкам realtime трафика, при одном ясном источнике авторитетного realtime состояния.

## Основные процессы

### Пакет Unity Editor

Обеспечивает Host, жизненный цикл подключения, Presence, поддерживаемые Transform/Lock и Hierarchy одной Scene, диагностику/восстановление и применение одобренного удалённого состояния к локальной Scene. Клиент **наблюдает authority**: локальное значение не становится авторитетным лишь потому, что существует в одном Editor.

### TeamForge Server

**Session Authority** управляет членством, общей ревизией/порядком, lock/lease, удерживаемым поддерживаемым состоянием Scene, защитой replay/идемпотентности и realtime эффектами. **Project Coordinator** управляет подписанными метаданными Project/Publisher/baseline/Peer. Server не хранит и не ретранслирует обычные данные Manifest/File/Chunk.

### Project Peer

Отвечает за подписанные приглашения, детерминированные manifest/hash, прямой HTTP, проверенное возобновление, staging, неизменяемые ревизии Active, безопасность файловой системы/путей и доверие Project/Publisher. Успешная загрузка недостаточна для активации: нужен весь путь проверки и доверия.

### Windows Guest Launcher

Новый Guest начинает вне Unity, потому что проекта для открытия может ещё не быть. Launcher проверяет встроенный Runtime, приглашение/доверие, принимает через Peer, проверяет финальный Active и требуемую Unity, затем передаёт управление. Обычному Guest из пакета не нужно устанавливать или вручную обслуживать системные Node.js/npm.

Текущие исходники Launcher также могут создать **ручной локальный пакет поддержки**: ограниченный наблюдательный ZIP с удалением чувствительных данных. Нет автоматической отправки, выдачи authority или обхода проверок приглашения, доверия, активации, Runtime, пути, Unity. Наличие функции в пакете зависит от точного артефакта; [Состояние](STATUS.ru.md) и [builds](../builds/README.md) разделяют источник/пакет.

## Host начинает сотрудничество

1. Выбирает **Publish & Start**.
2. Unity проверяет локальный проект и условия сохранённой Scene.
3. Peer готовит детерминированную baseline; файлы/chunk получают идентичности целостности.
4. Host Peer запускает Seed прямого переноса.
5. Метаданные Project/Publisher/baseline/Peer координируются с Server.
6. Создаётся подписанная Collaboration Invite; Host готов к Guest.

Есть дополнительные fail-closed проверки. **Host Ready — больше, чем открытый порт**: созданы контракты переноса и realtime сессии, нужные Guest. Приглашение не предназначено для кода доступа, закрытого ключа подписи или произвольного локального пути проекта. Код доступа, если нужен, передаётся отдельно.

## Новый Guest присоединяется

1. Открыть Windows Guest Launcher, проверить встроенный Runtime.
2. Загрузить/вставить приглашение, проверить структуру и подпись.
3. Проверить идентичность/доверие Project/Owner/Publisher.
4. Связаться с координированным Host/Seed, получить descriptor/manifest/inventory.
5. Скачать только нужные chunk, проверить целостность chunk/файлов/manifest/проекта.
6. Собрать в staging и проверить полный кандидат.
7. Создать неизменяемую ревизию Active, переместить маленький указатель текущего проекта.
8. Проверить нужный исполняемый файл Unity и финальную передачу; открыть проверенный проект.

Произвольный частично скачанный каталог не становится текущим проектом. Предыдущая проверенная Active может оставаться доступной во время приёма новой ревизии или при провале активации.

### Возобновление с учётом проверки

Уже проверенные данные можно использовать повторно там, где разрешает контракт. Это не доверие любому файлу на диске: hash и контракт активации остаются определяющими.

## Правка поддерживаемого объекта Scene

1. Пользователь двигает GameObject; служба Transform Unity замечает изменение.
2. Разрешается каноническая для authority идентичность объекта.
3. Проверяются lock/lease и authority текущего подключения; Transform отправляется по WebSocket.
4. Server проверяет операцию, применяет порядок/ревизию/идемпотентность.
5. Одобренный эффект рассылается другим клиентам.
6. Получатель обновляет Authority View; Unity безопасно применяет одобренный удалённый Transform.

**Идентичность:** оба Editor должны подразумевать один логический объект, не просто одинаковое имя/путь Hierarchy. Сохранённые объекты Scene используют стабильную Unity идентичность; поддерживаемые сессионные объекты могут получить TeamForge идентичность после авторитетной привязки. Неоднозначность ведёт к fail-closed, а не угадыванию по имени, индексу соседей или пути.

**Authority:** Server решает, какое общее realtime состояние принято. Клиенты сообщают намерения и применяют результаты, а не держат конкурирующие истины.

**Ревизия/порядок:** принятые операции продвигают общий порядок. Ревизии помогают оценить устаревание, поздний вход, replay и проверку операции относительно ожидаемого состояния.

**Lock/lease:** управляемые authority блокировки предотвращают молчаливую одновременную перезапись. Lease истекают при исчезновении клиента, не становятся вечными lock.

**Replay/идемпотентность:** допустимый повтор той же операции отличают от другой операции, повторно использующей идентичность. Двойная доставка не должна дважды менять состояние.

## Изменения Hierarchy

Создание/удаление/имя/родитель/порядок соседей внутри одной Scene используют отдельный авторитетный путь, а не имитируют Transform. Transform зависит от структуры: разные родители/идентичности могут дать разные Scene с одинаковыми локальными числами. Нельзя выводить из этого общую поддержку Component/Inspector/Prefab/Asset или произвольных межсценовых структур; см. [Состояние](STATUS.ru.md).

## Переподключение и эпохи подключения

Reconnect не доказывает действительность старой authority: потеря связи → перестать доверять authority подключения → reconnect/handshake → получить актуальные согласованные возможности и авторитетное состояние → заново привязать объекты для новой эпохи → продолжить только после готовности обязательного состояния. Сохранённые alias/кеш идентичностей помогают разрешению, но сами не дают authority.

## Ошибки и восстановление

Сохранять проверенное вместо принудительного принятия неизвестного:

- повреждённый Runtime: остановиться до исполнения непроверенного кода;
- неверное/конфликтующее приглашение: не менять существующую привязку Project;
- ошибка переноса: сохранить допустимый проверенный прогресс;
- ошибка активации: не заменять прежний проверенный Active;
- проблема пути Unity: только отдельно проверенная собственная стратегия TeamForge;
- несоответствие baseline/идентичности: требовать согласование/обновление, не угадывать;
- неизвестный процесс на нужном порту: не завершать его только потому, что TeamForge нужен порт.

Восстановление **зависит от состояния**. Retry, Paste New Invite, Use Latest Project, Open Existing Verified Project, Choose Unity предлагаются лишь там, где имеют определённый безопасный смысл.

**Диагностика — наблюдение, не полномочия восстановления.** Копия диагностики и ручной ZIP описывают запуск. Сохранение не меняет Project, не повторяет операцию, не доверяет Publisher, не активирует контент и не ослабляет проверки. Собирается ограниченное безопасное представление состояния, не широкие данные проекта/машины; перед публичной передачей всё равно нужна проверка.

## Зачем разделять перенос и realtime

Realtime нужны небольшие упорядоченные authority сообщения. Bootstrap включает много файлов, большие потоки, retry, возобновление, hash, staging и диск. Разделение предотвращает скрытое узкое место Server и проясняет границы безопасности/ошибок.

Цена — Host Peer должен реально быть доступен Guest. Подходят тот же ПК, достижимая LAN или управляемая VPN. Автоматические Internet discovery/NAT traversal/relay — отдельная будущая транспортная задача, не обещание в слове P2P.

## Где живёт состояние

| Состояние | Владелец/срок жизни |
| --- | --- |
| Realtime Session Authority | Память Server для живой сессии |
| Реестр координации Project | Память Server |
| Authority View клиента | Текущее подключение Unity |
| Данные переноса/staging | Управляемое хранилище Project Peer |
| Проверенные ревизии Active | Постоянное управляемое хранилище Project |
| Текущий указатель Active | Маленькие постоянные метаданные |
| История диагностики Launcher | Ограниченная история текущего запуска |
| Ручной пакет поддержки | Локальный ограниченный/очищенный ZIP пользователя; без автоматической отправки |

Постоянно скачанный проект не означает постоянную историю realtime authority; диагностический артефакт не становится authority. Это важно для restart, reconnect, возобновления и восстановления.

## От поведения к исходникам

Точные файлы/тесты ведёт [CODEMAP](../CODEMAP.md). Типовые пути: подключение → Unity `TeamForgeConnectionService` + Server WebSocket host; Transform/Lock → служба Transform + Authority View + Session Authority; Hierarchy → служба Unity + Server Hierarchy model/Session Authority; bootstrap/перенос → оркестраторы Host/Guest Peer + прямой источник + content store; старт/восстановление Guest → Windows Launcher + Launcher Core + Guest оркестратор; поддержка → UI диагностики + Core bundle/очистка; устойчивость путей → Launcher Core + общий контракт Project Peer. Ссылка на карту вместо копирования имён сохраняет объяснение полезным после рефакторинга.
