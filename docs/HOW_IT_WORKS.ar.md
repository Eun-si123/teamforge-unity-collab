# كيف يعمل TeamForge

تشرح هذه الصفحة **ما يحدث عند الاستضافة أو الانضمام أو نقل مشروع أو تعديل Scene أو انقطاع الاتصال أو التعافي من الفشل**. إنها شرح موجه، وليست مواصفة بروتوكول كاملة أو خريطة ملفات المصدر.

الإمكانات والعوائق: [الحالة](STATUS.ar.md)؛ البنية وحدود الثقة: [architecture](architecture.md)؛ الملفات: [CODEMAP](../CODEMAP.md)؛ أسباب القرارات: [architecture-decisions](architecture-decisions.md). تبقى التفاصيل غير المترجمة بالإنجليزية؛ [English](HOW_IT_WORKS.md) مرجع المعنى.

## النموذج في 60 ثانية

مساران للبيانات منفصلان عمدًا:

- يرسل Host/Guest Unity Editor عمليات realtime عبر WebSocket إلى Session Authority في Server.
- يستخدم Host Unity نظيره Host Project Peer/Seed ويستخدم Guest Launcher نظيره Guest Project Peer. تنتقل حمولة المشروع مباشرة عبر HTTP بين Peer؛ ثم يسلم Guest Peer مشروع Active متحققًا إلى Guest Unity.
- ينسق Server البيانات الوصفية الموقعة مع الطرفين، ولا يصبح وسيط ترحيل لملفات المشروع.
- لا يفتح Guest المحتوى إلا بعد نجاح فحوص الثقة وسلامة المحتوى والتفعيل والتسليم إلى Unity.

يُفصل النقل الكبير عن حركة التعاون الحساسة للتأخير، مع بقاء سلطة realtime واحدة واضحة.

## العمليات الرئيسية

### حزمة Unity Editor

توفر مسار Host ودورة الاتصال وPresence وتعاون Transform/Lock المدعوم وHierarchy داخل Scene واحدة، وعرض التشخيص/التعافي، وتطبيق الحالة البعيدة المعتمدة على Scene المحلية. العميل **يراقب السلطة**؛ لا تصبح القيمة المحلية مرجعية لمجرد وجودها في Editor واحد.

### TeamForge Server

تدير **Session Authority** العضوية والمراجعة/الترتيب المشترك وlock/lease وحالة Scene المدعومة المحتفظ بها وحماية replay/idempotency وتأثيرات realtime. يدير **Project Coordinator** بيانات التنسيق الموقعة لـ Project/Publisher/baseline/Peer. لا يخزن Server أو يرحل حمولة Manifest/File/Chunk المعتادة.

### Project Peer

يتولى التحقق من الدعوة الموقعة وmanifest/hash الحتمية وHTTP المباشر والاستئناف المتحقق وstaging ومراجعات Active غير القابلة للتغيير وأمان نظام الملفات/المسارات وثقة Project/Publisher. نجاح التنزيل وحده لا يكفي للتفعيل؛ يجب اجتياز مسار التحقق والثقة كاملًا.

### Windows Guest Launcher

يبدأ Guest الجديد خارج Unity لأن المشروع قد لا يكون موجودًا بعد. يتحقق Launcher من Runtime المرفق والدعوة والثقة، ويستقبل عبر Peer، ويفحص Active النهائي وإصدار Unity المطلوب ثم يسلم إلى Unity. لا يحتاج Guest المعتاد في الحزمة إلى تثبيت Node.js/npm النظام أو تشغيلهما يدويًا.

يستطيع مصدر Launcher الحالي أيضًا إنشاء **حزمة دعم محلية يدوية**: ملف ZIP رصدي محدود مع حجب البيانات الحساسة. لا رفع تلقائي ولا منح سلطة ولا تجاوز لفحوص الدعوة والثقة والتفعيل وRuntime والمسار وتسليم Unity. وجود الإجراء في حزمة منشورة يعتمد على الملف المحدد؛ تفصل [الحالة](STATUS.ar.md) و[builds](../builds/README.md) بين المصدر والحزم.

## عندما يبدأ Host التعاون

1. يختار **Publish & Start**.
2. يتحقق Unity من المشروع المحلي ومتطلبات Scene المحفوظة.
3. يعد Peer خط أساس حتميًا، وتُمنح الملفات وchunk هويات سلامة.
4. يبدأ Host Peer خدمة Seed للنقل المباشر.
5. تُنسق بيانات Project/Publisher/baseline/Peer مع Server.
6. تُنشأ Collaboration Invite موقعة؛ يصبح Host جاهزًا للضيوف.

توجد فحوص fail-closed إضافية. **Host Ready يعني أكثر من فتح منفذ**: أُنشئت عقود النقل وجلسة realtime المطلوبة لمسار Guest. الدعوة ليست لنقل رمز الوصول أو مفتاح التوقيع الخاص أو مسار مشروع محلي اعتباطي. يُشارك رمز الوصول منفصلًا عند استخدامه.

## عندما ينضم Guest جديد

1. فتح Windows Guest Launcher والتحقق من Runtime المرفق.
2. تحميل/لصق الدعوة، ثم فحص بنيتها وتوقيعها.
3. فحص هوية وثقة Project/Owner/Publisher.
4. الاتصال بـ Host/Seed المنسق، واستلام descriptor/manifest/inventory.
5. تنزيل chunk المطلوبة فقط؛ والتحقق من سلامة chunk والملف وmanifest والمشروع.
6. البناء في staging والتحقق من المرشح الكامل.
7. إنشاء مراجعة Active غير قابلة للتغيير؛ وتحريك مؤشر المشروع الحالي الصغير.
8. التحقق من ملف Unity التنفيذي المطلوب والتسليم النهائي؛ وفتح المشروع المتحقق.

لا يُعامل مجلد اعتباطي نُزّل جزئيًا كمشروع حالي. يمكن أن تبقى مراجعة Active السابقة المتحققة متاحة أثناء استقبال الجديدة أو فشل التفعيل.

### الاستئناف يراعي التحقق

يمكن إعادة استخدام محتوى سبق التحقق منه حيث يسمح عقد النقل. هذا لا يعني الثقة بأي ملف موجود على القرص؛ تظل hash وعقد التفعيل مرجع القرار.

## تعديل كائن Scene مدعوم

1. يحرك المستخدم GameObject؛ تلاحظ خدمة Transform في Unity التغيير.
2. تُحل هوية الكائن المرجعية وفق السلطة.
3. يُفحص lock/lease وسلطة الاتصال الحالي؛ وتُرسل عملية Transform عبر WebSocket.
4. يتحقق Server من العملية ويطبق قواعد الترتيب/المراجعة/idempotency.
5. يبث الأثر المعتمد إلى العملاء الآخرين.
6. يحدث المستلم Authority View؛ ويطبق Unity التحويل البعيد المعتمد بأمان.

**الهوية:** يجب أن يقصد Editor في الطرفين الكائن المنطقي نفسه، لا مجرد اسم أو مسار Hierarchy متطابق. تستخدم كائنات Scene المحفوظة هوية Unity ثابتة؛ ويمكن لكائنات الجلسة المدعومة الحصول على هوية TeamForge بعد الربط المرجعي. الغموض يؤدي إلى fail-closed بدل التخمين بالاسم أو فهرس الأشقاء أو المسار.

**السلطة:** يقرر Server الحالة المشتركة المقبولة في realtime. يبلغ العملاء النوايا ويطبقون النتائج، ولا يحتفظ كل منهم بحقيقة منافسة مستقلة.

**المراجعة والترتيب:** تقدم العمليات المقبولة الترتيب المرجعي المشترك. تساعد معلومات المراجعة في فهم الحالة القديمة والانضمام المتأخر وreplay، وهل قُيمت العملية مقابل الحالة المشتركة المتوقعة.

**Lock/lease:** تتحكم السلطة في الأقفال لمنع الكتابة المتزامنة الصامتة فوق الكائن نفسه. تنتهي lease عند اختفاء العميل بدل أن تصبح أقفالًا دائمة.

**Replay/idempotency:** تُميز إعادة المحاولة المشروعة للعملية نفسها عن عملية مختلفة تعيد استخدام هوية. لا ينبغي أن يعدّل تسليم الرسالة مرتين الحالة مرتين.

## تغييرات Hierarchy

تستخدم عمليات الإنشاء/الحذف/التسمية/تغيير الأصل/ترتيب الأشقاء داخل Scene نفسها مسار سلطة منفصلًا، ولا تتظاهر بأنها Transform عادية. يعتمد Transform على البنية؛ اختلاف الأصل أو الهوية قد ينتج Scene مختلفة رغم تطابق الأرقام المحلية. لا تستنتج دعم Component/Inspector/Prefab/Asset العام أو بنى اعتباطية عبر Scene؛ راجع [الحالة](STATUS.ar.md).

## إعادة الاتصال وحقب الاتصال

إعادة الاتصال ليست دليلًا على صلاحية السلطة القديمة: فقد الاتصال → إيقاف الثقة بسلطة نطاق الاتصال → reconnect/handshake → استلام الإمكانات المتفاوض عليها والحالة المرجعية الحالية → إعادة ربط الكائنات المدعومة للحقبة الجديدة → استئناف التعاون فقط بعد جاهزية الحالة المطلوبة. قد تساعد alias المحفوظة أو ذاكرة الهوية المحلية في الحل، لكنها لا تمنح سلطة بنفسها.

## الفشل والتعافي

الحفاظ على حالة متحققة بدل إجبار حالة مجهولة على المرور:

- Runtime تالف: التوقف قبل تنفيذ كود حزمة غير متحقق؛
- دعوة غير صالحة/متعارضة: إبقاء ربط Project الحالي دون تغيير؛
- فشل النقل: حفظ التقدم المتحقق المسموح بإعادة استخدامه؛
- فشل التفعيل: عدم استبدال Active السابق المتحقق؛
- مشكلة مسار Unity: استراتيجية مسار مملوكة لـ TeamForge ومتحقق منها منفصلًا فقط؛
- عدم تطابق baseline/الهوية: طلب التسوية/التحديث بدل التخمين؛
- عملية مجهولة على منفذ مطلوب: لا تُنهها لمجرد أن TeamForge يريد المنفذ.

التعافي **محكوم بالحالة**. لا تُعرض Retry وPaste New Invite وUse Latest Project وOpen Existing Verified Project وChoose Unity إلا في حالات لها معنى آمن محدد.

**التشخيص ملاحظة، وليس سلطة تعافٍ.** نسخ التشخيص وZIP اليدوي يصفان التشغيل. حفظ الحزمة لا يغير Project المختار ولا يعيد عملية ولا يثق بـ Publisher ولا يفعل المحتوى ولا يخفف الفحوص. يجمع منظور حالة آمنًا محدودًا بدل بيانات مشروع/جهاز واسعة؛ ومع ذلك يجب مراجعته قبل النشر العام.

## لماذا ينفصل النقل عن realtime

يستفيد realtime من رسائل سلطة صغيرة مرتبة. يتضمن bootstrap ملفات كثيرة وتدفقات كبيرة ومحاولات واستئنافًا وhash وstaging وعمل القرص. يمنع الفصل تحوّل بايتات المشروع إلى عنق زجاجة خفي في Server ويوضح حدود الأمان والفشل.

المقابل أن Guest يجب أن يصل فعلًا إلى Host Peer. يناسب النقل الحالي الجهاز نفسه أو LAN يمكن الوصول إليها أو VPN مُدارة. discovery للإنترنت وعبور NAT وrelay التلقائية مشكلة نقل مستقبلية مستقلة، وليست وعدًا ضمنيًا في كلمة P2P.

## مكان الحالة وعمرها

| الحالة | المالك/العمر |
| --- | --- |
| Session Authority لـ realtime | ذاكرة Server طوال الجلسة الحية |
| سجل تنسيق Project | ذاكرة Server |
| Authority View للعميل | اتصال Unity الحالي |
| محتوى النقل/staging | تخزين Project Peer المُدار |
| مراجعات Active المتحققة | تخزين Project مُدار ودائم |
| مؤشر Active الحالي | بيانات وصفية صغيرة دائمة |
| تاريخ تشخيص Launcher | تاريخ محدود للتشغيل الحالي |
| حزمة دعم يدوية | ZIP محلي محدود/محجوب ينشئه المستخدم؛ لا رفع تلقائي |

استمرار المشروع المُنزّل لا يعني استمرار تاريخ سلطة realtime، وملف التشخيص لا يصبح سلطة تعاون. يهم هذا الفصل عند إعادة التشغيل والاتصال والاستئناف والتعافي.

## تتبع السلوك إلى المصدر

تحتفظ [CODEMAP](../CODEMAP.md) بأسماء الملفات والاختبارات الدقيقة. مسارات نموذجية: الاتصال → Unity `TeamForgeConnectionService` + مضيف WebSocket في Server؛ Transform/Lock → خدمة Transform + Authority View + Session Authority؛ Hierarchy → خدمة Unity + نموذج Hierarchy في Server/Session Authority؛ bootstrap/النقل → منسقات Host/Guest Peer + المصدر المباشر + مخزن المحتوى؛ بدء/تعافي Guest → Windows Launcher + Launcher Core + منسق Guest؛ الدعم → واجهة التشخيص + مسار الحزمة/حجب البيانات في Core؛ تحمل المسارات → Launcher Core + عقد Project Peer المشترك. الرجوع إلى خريطة الكود بدل نسخ أسماء الملفات هنا يبقي الشرح مفيدًا بعد إعادة الهيكلة.
