> 🚧 **초기 공개 프리뷰 — 개발 중**
>
> TeamForge는 현재 적극적으로 개발 중입니다. 이 저장소는 지금 단계에서는 아이디어를 설명하고, 개발 진행 상황을 보여주고, 솔직한 피드백을 받고, 더 많은 사람이 오픈소스 형태로 함께 검토하고 기여할 수 있도록 준비하기 위한 목적이 큽니다.
>
> **아직 전체 개발 소스가 이 공개 저장소에 올라온 상태는 아니며, 완성된 제품이나 실제 프로젝트에 바로 사용할 수 있는 안정적인 도구로 받아들이면 안 됩니다.**

**TeamForge** *(임시 이름)* 는 **Unity Editor**를 위한 실험적인 협업 도구입니다.

아이디어는 단순합니다. 여러 사람이 같은 Unity 프로젝트를 함께 작업할 때, 지금보다 훨씬 즉각적이고 덜 번거롭게 만들고 싶었습니다.

협업이 단순히:

> 수정 → 저장 → 커밋 → 푸시 → 풀 → 충돌 해결 → 반복

만으로 이루어지는 것이 아니라, 여러 사람이 같은 프로젝트에 연결되어 일부 Editor 변경 사항을 실시간으로 확인하고, 다른 개발자가 프로젝트를 받아 참여하는 과정도 더 간단하게 만드는 흐름을 실험하고 있습니다.

## TeamForge를 만들게 된 이유

TeamForge는 처음부터 공개 개발 도구를 만들겠다는 계획으로 시작한 프로젝트가 아닙니다.

저는 친구와 함께 어떤 사례/이야기에서 영감을 받은 Unity 게임 프로젝트를 만들고 있었습니다. 둘이 같이 게임을 만들고 싶었지만, 실제로 같은 Unity 프로젝트를 함께 작업하는 과정은 생각보다 훨씬 불편했습니다. 같은 Editor 안에서 자연스럽게 나란히 작업할 수 있는 것도 아니고, 프로젝트 상태를 계속 주고받거나 파일을 기다리거나 누가 무엇을 수정하고 있는지 맞춰 가는 과정이 답답했습니다.

그래서 처음 TeamForge를 만들기 시작한 이유는 단순했습니다.

**친구와 제가 같이 쓰기 편한 도구가 필요했기 때문입니다.**

그런데 만들다 보니 생각이 조금 바뀌었습니다.

“이게 우리 둘만 불편한 걸까?”라는 생각이 들었습니다. 저와 제 친구가 Unity 협업 때문에 불편했다면, 다른 친구끼리 만드는 팀이나 학생, 소규모 팀, 인디 개발자들도 비슷한 문제를 겪고 있을 수 있다고 생각했습니다.

그래서 TeamForge를 단순히 둘만 쓰는 개인 도구로 남겨두는 대신, **다른 사람들도 사용할 수 있고, 소스를 확인하고, 개선하고, 함께 기여할 수 있는 프로젝트**로 만들어 보기로 했습니다.

이 GitHub 저장소는 그렇게 방향을 바꾸면서 만들어졌습니다.

## 어떤 문제를 해결하려고 하나요?

버전 관리는 매우 유용하며, TeamForge는 **Git이나 다른 버전 관리 시스템을 대체하려는 도구가 아닙니다.**

하지만 버전 관리와 실시간 협업은 서로 다른 문제를 해결합니다.

두 사람이 Unity 프로젝트를 가까이 붙어서 같이 작업하다 보면 이런 순간이 생깁니다.

- "지금 어떤 버전의 프로젝트 가지고 있어?"
- "프로젝트 좀 보내줄래?"
- "이 오브젝트 네가 움직였어, 내가 움직였어?"
- "지금 이 Scene 수정 중이야?"
- "왜 네 컴퓨터에서는 되는데 내 컴퓨터에서는 안 되지?"
- 다른 사람이 작업을 시작하기도 전에 프로젝트 파일 복사나 동기화를 기다려야 하는 상황

TeamForge는 **실시간 Editor 협업**과 **프로젝트 준비/전송 도구**를 함께 사용해서 이런 마찰을 줄일 수 있는지 실험하고 있습니다.

## 현재 어떤 기능을 실험하고 있나요?

현재 프로토타입은 다음과 같은 기능을 중심으로 개발되고 있습니다.

- **Presence** — 현재 연결된 다른 협업자 확인
- **Selection / Editor awareness** — 다른 사용자가 무엇을 보고 있거나 작업 중인지 확인
- **Transform 동기화** — 위치, 회전, 크기 변경을 Editor 사이에서 공유
- **기본 오브젝트 잠금 / 소유권** — 서로 충돌하는 편집 감소
- **Project bootstrap** — 다른 개발자가 참여에 필요한 프로젝트를 받을 수 있도록 지원
- **직접 P2P 프로젝트 전송 실험**
- **청크 전송, 무결성 검사, 이어받기, 복구 실험**
- 동기화나 전송 실패 시 사용할 수 있는 **진단 및 복구 UX**

일부 기능은 현재 개발 빌드에서 실제로 작동하고 있지만, **기능이 존재한다고 해서 완성되었거나 안전하거나 일반적인 실제 프로젝트에서 사용해도 된다는 뜻은 아닙니다.**

공개 프리뷰를 준비하면서 더 많은 기능과 자세한 개발 상태를 정리할 예정입니다.

## 로드맵

TeamForge는 기본적인 Transform 동기화에서 끝나는 프로젝트로 계획하고 있지 않습니다. 현재는 기존 협업 및 Project bootstrap 기반을 먼저 안정화한 뒤, 더 깊은 Scene / Hierarchy / Inspector / Prefab / Asset 협업과 복구, 네트워킹, 보안 기능으로 확장하는 방향을 잡고 있습니다.

로드맵은 **출시 날짜나 기능 구현을 보장하는 약속이 아니라 개발 방향**입니다. 테스트나 외부 피드백을 통해 다른 문제가 더 중요하다고 판단되면 우선순위는 바뀔 수 있습니다.

## 최종적으로 원하는 사용 흐름

장기적으로는 대략 이런 느낌을 목표로 하고 있습니다.

1. 한 개발자가 Unity 프로젝트를 엽니다.
2. TeamForge 세션을 시작합니다.
3. 다른 개발자를 초대합니다.
4. 초대받은 개발자가 참여에 필요한 프로젝트를 받습니다.
5. 두 Unity Editor가 연결됩니다.
6. 유용한 프로젝트 및 Scene 변경 사항을 계속 수동으로 주고받지 않고 협업 형태로 확인합니다.

이 여섯 단계 안에는 생각보다 많은 기술적 문제와 안전 문제가 숨어 있습니다. TeamForge는 그런 문제를 없는 척하기보다 직접 해결 가능한지 실험해 보는 프로젝트입니다.

## AI 개발 투명성

이 프로젝트는 **AI 보조 / AI 생성 프로그래밍을 매우 적극적으로 활용해서 개발하고 있습니다.**

이 저장소의 문서와 공개용 글 역시 AI의 도움을 상당히 받아 작성하고 있습니다. 게시되는 내용은 제가 직접 검토하고 수정하며 최종 결정을 내리지만, AI가 만든 실수나 어색한 표현, 부정확한 설명이 남아 있을 수 있습니다.

저는 **숙련된 프로그래머가 아닙니다.** 그래서 모든 코드를 제가 직접 작성했거나 전문적으로 검토했다고 오해하게 만들고 싶지 않습니다.

제가 주로 하는 역할은 다음과 비슷합니다.

- 프로그램이 무엇을 해야 하는지 결정하기
- 사용 흐름과 요구사항 설계 및 수정
- AI 도구를 이용해 요구사항 구현 보조
- 실제 환경에서 프로그램 실행
- 버그 재현 및 로그 / 실패 사례 제공
- 단순히 컴파일된다는 이유만으로 생성된 코드를 받아들이지 않고 반복 테스트
- 가능한 경우 자동화 테스트 실행
- 여러 Unity Editor 인스턴스와 테스트 프로젝트에서 기능이 실제로 의도대로 작동하는지 확인

이런 검증은 의미가 있지만 한계도 있습니다.

**모든 프로그래밍 실수, 설계 문제, 보안 문제, 경쟁 상태, 데이터 손실 가능성, 예외 상황을 제가 전부 찾아낼 수 있다고 보장할 수 없습니다.** 또한 전문적인 보안 감사나 독립적인 코드 리뷰를 완료했다고 주장하지 않습니다.

AI 사용 사실을 숨기지 않고 개발 과정을 명확하게 밝히는 이유 중 하나도 이것입니다.

Unity, 네트워킹, 보안, 개발 도구 분야의 경험이 있는 분들의 기술적인 비판과 의견은 특히 환영합니다.

## TeamForge를 다른 사람에게 알려주세요

TeamForge가 유용해 보이거나, 같은 Unity 프로젝트를 다른 사람과 함께 작업하면서 불편함을 겪었던 개발자를 알고 있다면 이 저장소를 그분에게 공유해 주시면 정말 감사하겠습니다.

특히 소규모 팀, 학생 개발자, 인디 개발자, 테스터, 그리고 기술적인 피드백이나 코드 검토를 도와줄 수 있는 경험 있는 개발자들에게 TeamForge가 알려졌으면 합니다.

어디에 무리하게 홍보하거나 스팸처럼 퍼뜨릴 필요는 없습니다. **실제로 관심을 가질 만한 사람 한 명에게 알려주는 것만으로도 큰 도움이 됩니다.**

직접 사용할 생각이 없더라도 솔직한 의견을 남기거나, 관심 있어 할 만한 사람에게 공유해 주는 것만으로 TeamForge를 계속 개발할 가치가 있는지, 앞으로 어떤 방향으로 가야 할지 판단하는 데 도움이 됩니다.

## 현재 안전성 / 완성도 안내

⚠️ **TeamForge는 실험적인 소프트웨어로 취급해 주세요.**

프로젝트가 훨씬 더 안정적인 단계에 도달하기 전까지는:

- 중요한 프로젝트의 유일한 사본에 의존하지 마세요.
- 백업본이나 버려도 되는 테스트 프로젝트에서 사용하세요.
- 버그와 미완성 동작이 있을 수 있다고 예상해 주세요.
- 네트워크 및 동기화 동작은 변경될 수 있습니다.
- 개발 버전 사이의 호환성이 변경될 수 있습니다.

이 공개 프리뷰의 목적은 준비가 되지도 않았는데 완성품처럼 보이게 만드는 것이 아니라, **무엇이 실제로 유용한지 먼저 배우는 것**입니다.

## 왜 완성되기 전에 공개하나요?

Unity 개발자들이 실제로 원하지 않는 것을 오랫동안 만들고 싶지 않기 때문입니다.

그래서 완성된 척하기보다 아이디어를 일찍 보여주고 묻고 싶습니다.

### 실제로 이런 도구를 사용하시겠습니까?

특히 이런 질문에 대한 답이 궁금합니다.

- 현재 Unity 프로젝트에서 다른 사람과 어떻게 협업하고 있나요?
- 다른 Unity 개발자와 작업할 때 가장 불편한 부분은 무엇인가요?
- 실시간 Scene / Editor 협업이 실제로 도움이 될까요?
- 실시간 편집보다 간편한 프로젝트 공유 / 프로젝트 준비 기능이 더 유용할까요?
- 어떤 이유가 있으면 이런 도구를 절대 사용하지 않을 것 같나요?
- 실제 프로젝트에서 TeamForge를 신뢰하려면 무엇이 필요할까요?
- 초기 Alpha 버전이 준비되면 테스트해 볼 의향이 있나요?

긍정적인 피드백도 도움이 되지만 **부정적인 피드백도 중요합니다.** 잘못된 문제를 해결하고 있다면 지금 알아내는 편이 낫습니다.

**[Would you use TeamForge? Early feedback wanted](https://github.com/Eun-si123/teamforge-unity-collab/issues/1)** 이슈에서도 의견을 남길 수 있습니다.

## 오픈소스 방향과 라이선스

TeamForge는 **GNU Affero General Public License version 3 (AGPLv3)** 기반의 오픈소스 프로젝트로 준비하고 있습니다.

아직 전체 개발 소스가 이 공개 저장소에 올라오지는 않았지만, 최종적으로 소스를 닫아두는 것이 아니라 공개하는 방향입니다.

AGPLv3를 선택한 이유 중 하나는 TeamForge가 네트워크 기능을 포함하는 소프트웨어이기 때문입니다. TeamForge의 적용 대상이 되는 수정본이 다른 사람에게 배포되거나, 수정된 버전이 네트워크를 통해 사용자와 상호작용하는 경우에도 해당 라이선스의 소스 제공 의무가 적용될 수 있도록 하여, 수정본이 완전히 닫힌 블랙박스로 바뀌는 것을 줄이고 싶습니다.

## 개발 속도에 대하여

TeamForge는 **회사나 풀타임 업무로 운영되는 프로젝트가 아니라 개인 오픈소스 프로젝트**입니다. 저는 현재 학생이기 때문에 학교, 시험뿐 아니라 휴식, 친구들과 보내는 시간, 게임 같은 취미와 다른 일상생활에 시간을 쓰면서 개발하고 있습니다. 그래서 시기에 따라 개발 속도가 느려지거나 잠시 멈출 수 있습니다.

한동안 커밋이나 업데이트가 없다고 해서 **곧바로 프로젝트를 포기했다는 뜻은 아닙니다.** 계속 업데이트하는 척하기보다 오래 유지할 수 있는 속도로 TeamForge를 개발하고 싶습니다.

따라서 로드맵은 마감일이 아니라 개발 방향으로 봐 주세요. 개발이 느린 시기에도 테스트, 리뷰, 문서 개선과 외부 기여는 언제든 환영합니다.
