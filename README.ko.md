> TeamForge는 현재 적극적으로 개발 중입니다. 개발 환경에서는 프로토타입 기능들이 작동하고 있지만, **전체 개발 소스와 공개 Alpha는 아직 이 저장소에 공개되지 않았습니다.** 중요한 Unity 프로젝트의 유일한 사본에 TeamForge를 의존하지 마세요.

**TeamForge** *(임시 이름)* 는 **Unity Editor**를 위한 실험적인 협업 도구입니다. 여러 사람이 같은 Unity 프로젝트를 작업할 때 일부 Editor 변경 사항을 실시간으로 확인하고, 기존 프로젝트에 다른 개발자가 참여하는 과정도 지금보다 덜 번거롭게 만드는 흐름을 실험하고 있습니다.

## TeamForge를 만들게 된 이유

TeamForge는 처음부터 공개 개발 도구를 만들겠다는 계획으로 시작한 프로젝트가 아닙니다.

저는 친구와 Unity 게임을 만들고 있었습니다. 둘이 같은 프로젝트를 함께 작업하고 싶었지만, 실제 과정은 생각보다 훨씬 불편했습니다. 프로젝트 상태를 계속 주고받고, 파일을 기다리고, 누가 무엇을 바꿨는지 맞춰 가고, 서로 같은 프로젝트 상태를 유지하는 과정이 번거로웠습니다.

그래서 처음 TeamForge를 만들기 시작한 이유는 단순했습니다.

**친구와 제가 같이 쓰기 편한 도구가 필요했기 때문입니다.**

그런데 만들다 보니 “이게 우리 둘만의 문제일까?”라는 생각이 들었습니다. 다른 친구끼리 만드는 팀, 학생, 소규모 팀, 인디 개발자들도 비슷한 불편을 겪을 수 있습니다. 그래서 TeamForge를 둘만 쓰는 개인 도구로 남겨두는 대신, 다른 사람들도 **사용하고, 소스를 확인하고, 개선하고, 테스트하고, 기여할 수 있는 프로젝트**로 만들어 보기로 했습니다.

## 어떤 문제를 해결하려고 하나요?

버전 관리는 매우 유용하며, TeamForge는 **Git, Unity Version Control 또는 다른 버전 관리 시스템을 대체하려는 도구가 아닙니다.**

버전 관리와 실시간 협업은 서로 다른 부분의 문제를 해결합니다. TeamForge는 Unity Editor에서 가까이 붙어서 함께 작업할 때 생기는 이런 마찰에 집중합니다.

- "지금 어떤 버전의 프로젝트 가지고 있어?"
- "프로젝트 좀 보내줄래?"
- "이 오브젝트 네가 움직였어, 내가 움직였어?"
- "지금 이 Scene 수정 중이야?"
- "왜 네 컴퓨터에서는 되는데 내 컴퓨터에서는 안 되지?"
- 다른 개발자가 작업을 시작하기도 전에 프로젝트 파일을 기다려야 하는 상황

TeamForge는 **실시간 Editor 협업**과 **프로젝트 준비 / 전송 도구**를 함께 사용해 이런 불편을 줄일 수 있는지 실험합니다. 동시에 실패, 복구, 신뢰 경계를 숨겨진 “마법”처럼 처리하지 않고 사용자가 이해할 수 있게 만드는 것도 중요하게 보고 있습니다.

## 목표로 하는 사용 흐름

장기적으로 일반적인 사용 흐름은 대략 이런 느낌을 목표로 합니다.

1. Unity 프로젝트를 엽니다.
2. Start Collaboration을 누릅니다.
3. 다른 개발자를 초대합니다.
4. 초대받은 개발자가 참여에 필요한 프로젝트를 받습니다.
5. 두 Editor가 연결됩니다.
6. 유용한 프로젝트 및 Scene 변경 사항을 계속 수동으로 주고받지 않고 협업 형태로 확인합니다.

이 여섯 단계 안에는 동기화, 객체 식별, 네트워킹, 보안, 복구와 관련된 어려운 문제가 많이 숨어 있습니다. TeamForge는 그 문제들을 실제로 해결할 수 있는지 진지하게 실험하는 프로젝트입니다.

## TeamForge가 아닌 것

현재 TeamForge는 다음과 같은 것이 **아닙니다**.

- 버전 관리나 백업을 대체하는 도구
- 완성된 상용 수준의 협업 플랫폼
- 독립적인 전문 보안 감사를 완료한 소프트웨어
- 데이터 손실, 악성 Peer, 구현 실수, 모든 예외 상황에 대해 안전성이 보장된 도구
- 로드맵의 모든 항목을 반드시 구현하겠다는 약속

현재 목표는 프로젝트가 모두에게 준비됐다고 주장하는 것이 아니라, **사용 흐름과 기술적 접근이 실제로 가치가 있는지 먼저 검증하는 것**입니다.

## 피드백을 받고 싶습니다

TeamForge를 완성된 뒤에 처음 공개하기보다 지금 일찍 공개한 이유는, **잘못된 아이디어라면 엄청난 시간을 쓰기 전에 알고 싶기 때문입니다.**

긍정적인 의견뿐 아니라 **부정적인 의견도 유용합니다.** **[Would you use TeamForge? Early feedback wanted](https://github.com/Eun-si123/teamforge-unity-collab/issues/1)** 에 답하거나 Discussion을 시작해 주세요.

## AI 개발 투명성

TeamForge는 구현과 문서를 포함해 **AI의 도움을 상당히 많이 받아 개발하고 있습니다.**

저는 숙련된 프로그래머가 아니며 모든 코드가 제가 직접 손으로 작성되었거나 전문적인 검토를 거쳤다고 보이게 만들고 싶지 않습니다. 제가 주로 맡는 역할은 다음과 같습니다.

- 제품 목표, 요구사항, 사용 흐름 결정
- 구현 방향을 지시하고 결과 검토
- 실제 환경에서 프로그램 실행
- 버그 재현 및 실패 사례 수집
- 단순히 컴파일된다는 이유만으로 생성된 코드를 받아들이지 않고 반복 테스트
- 가능한 경우 자동화 테스트 실행
- 최종 프로젝트 및 릴리스 결정

이런 작업은 의미가 있지만 경험 많은 외부 개발자의 독립적인 검토를 대신하지는 못합니다. 모든 설계 문제, 경쟁 상태, 보안 취약점, 데이터 손실 가능성, 예외 상황을 제가 전부 찾아낼 수 있다고 보장할 수 없습니다.

AI를 사용한 기여도 환영합니다. 다만 기여자는 자신이 제출하는 내용을 실제로 검토하고 테스트하고 책임질 수 있어야 합니다. 자세한 내용은 **[CONTRIBUTING.md](CONTRIBUTING.md)** 를 확인해 주세요.

## 안전 및 보안

현재 TeamForge 빌드는 모두 실험적인 소프트웨어로 취급해 주세요.

- 백업을 유지하세요.
- 초기 테스트에는 버려도 되는 프로젝트 복사본을 사용하는 것을 권장합니다.
- 미완성 동작과 호환성 변경을 예상해 주세요.
- 로그에 자격 증명, Access Token, Invite Secret 또는 다른 민감한 정보를 공개하지 마세요.
- 출처를 알 수 없는 Fork나 빌드는 신뢰할 이유가 생기기 전까지 신뢰하지 마세요.

보안과 관련된 민감한 신고는 **[SECURITY.md](SECURITY.md)** 를 따라 주세요.

## 오픈소스 방향과 라이선스

TeamForge는 **GNU Affero General Public License version 3 (AGPLv3)** 기반의 오픈소스 프로젝트로 준비하고 있습니다.

전체 개발 소스는 공개 전에 아직 정리 및 검토 중입니다. 현재 저장소는 문서, 데모, 피드백, 라이선스, 기여 가이드, 개발 방향을 위한 공개 프로젝트 홈 역할을 합니다.

TeamForge는 네트워크 기능을 가진 소프트웨어이기 때문에, 수정된 적용 대상 버전의 소스를 확인할 수 없는 폐쇄형 블랙박스로 바뀌는 것을 원하지 않아 AGPLv3를 선택했습니다. 하지만 **오픈소스라는 사실 자체가 해당 빌드의 안전성을 보장하지는 않습니다.**

적용되는 라이선스 조건을 지키는 한 TeamForge 코드를 Fork, 수정, 재배포하거나 상업적으로 사용하는 것 자체를 금지하지 않습니다. 이 프로젝트에서 중요하게 보는 부분은 실제 프로젝트의 역사와 기여 출처를 정확하게 남기는 것입니다.

## 개발 속도에 대해

TeamForge는 **개인 오픈소스 프로젝트이며 전업 업무나 회사가 지원하는 제품이 아닙니다.** 저는 현재 학생이기 때문에 학교, 시험, 휴식, 친구, 게임, 다른 취미나 일상생활 때문에 개발 속도가 느려지거나 잠시 멈출 수 있습니다.

한동안 업데이트가 없다고 해서 **자동으로 프로젝트가 버려졌다는 뜻은 아닙니다.** 계속 업데이트하겠다고 무리하게 약속하기보다 지속 가능한 속도로 개발하고 싶습니다.
