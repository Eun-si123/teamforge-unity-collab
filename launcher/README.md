# TeamForge Guest Launcher 0.5.1 (Windows x64)

This directory contains the **source and tests** for the standalone Windows Guest Launcher used by the current `0.5.1-wp5.1-path-resilience` candidate lineage.

The generated `launcher/win-x64/` folder shown below is a **packaged release layout**. It is intentionally not committed to the public source checkout. A fresh clone therefore contains the launcher project, runtime loader, and tests, but not a ready-to-run `TeamForge.Launcher.exe` or generated bundled Runtime.

The launcher is a .NET 10 WPF application published as a self-contained **folder**, not a single-file app. WP5.1 adds path-resilience/automatic-short-workspace handling around the established Guest flow; it does not change the Project Transfer or realtime protocol versions.

## Trusted packaged layout

After the release packaging step, the published folder is intentionally closed over these app-owned paths:

```text
win-x64/
  TeamForge.Launcher.exe
  runtime-loader.mjs
  Runtime/
    runtime-manifest.json
    platforms/win-x64/node.exe
    backend/...
  <self-contained .NET files>
```

There is no PATH, system Node/npm, project-local runtime, source-workspace, or `TEAMFORGE_WORKSPACE_ROOT` fallback in the normal packaged execution path. `RuntimePins.g.cs` must be regenerated by the packaging step after `Runtime/` and `runtime-loader.mjs` are final.

A development checkout may contain placeholder generated pins before packaging. Those placeholders deliberately fail packaged-runtime startup and are forbidden in a release candidate. The packaged launcher verifies the compiled manifest/loader pins, then verifies the manifest-pinned Node executable and allowlisted runtime files before starting the bridge.

The runtime manifest's `guestBridgeRelativePath` must be exactly `backend/project-peer/src/guest-orchestrator-cli.mjs`.

## Build and focused tests

Source developers can build the generated folder with:

```powershell
dotnet restore launcher/src/TeamForge.Launcher/TeamForge.Launcher.csproj -r win-x64
dotnet run --project launcher/tests/TeamForge.Launcher.Core.Tests/TeamForge.Launcher.Core.Tests.csproj -c Release
dotnet publish launcher/src/TeamForge.Launcher/TeamForge.Launcher.csproj -c Release -r win-x64 --self-contained true --no-restore -o launcher/win-x64
```

A plain `dotnet publish` creates the .NET publish output, but a TeamForge release candidate additionally requires the repository's runtime packaging/pin/manifest steps. Do not treat an arbitrary local publish directory as the official current candidate.

After complete packaging and pin generation, this exercises the same runtime verifier, environment scrubber, absolute executable policy, and bridge used by the UI:

```powershell
launcher/win-x64/TeamForge.Launcher.exe --self-test-runtime
```

Success writes one JSON line with `{"ok":true,...}` and exits 0. Failure writes `{"ok":false,"code":"..."}` and exits nonzero. Release verification should also exercise hostile environment input such as `NODE_OPTIONS` and confirm that the packaged environment policy prevents it from affecting the verified child runtime.

## Path-resilience boundary

The current WP5.1 candidate is designed around a bounded, managed Windows execution/workspace path rather than assuming arbitrary path depth will work forever.

- The packaged/runtime path budget remains finite; unusually deep extraction or destination paths are not a supported promise.
- Korean characters and spaces are part of the tested candidate path model.
- Automatic short-workspace handling exists to keep execution paths within the release contract without weakening final project-path validation.
- Path shortening/aliasing is an execution detail, not permission to escape the managed destination, bypass hash checks, or launch an unverified project.

## Security and UX boundaries

- The default managed destination is the Windows Documents known folder plus `TeamForge Projects`; launcher state, trust, and one-time handoff files live below Local AppData `TeamForge/Launcher`.
- Invite and access-code values are sent only as bounded NDJSON over stdin. They are never CLI arguments, persisted launcher state, or raw stderr logs.
- Trust is an explicit Publisher/Project challenge. Full Owner and Publisher fingerprints remain under Advanced details, including prior fingerprints on mismatch.
- Unity is opened only for a bridge-returned, revalidated `<uuid>/active/<revision>-<manifest-prefix>` path and a handoff under `guest-core/handoff`. The exact `ProjectVersion.txt` version is probed before launch. Paths are passed through `ProcessStartInfo.ArgumentList` with shell execution disabled.
- Legacy transfer-only invites are rejected before receive because they cannot complete the required realtime handoff. The Host must provide a Host Ready Collaboration Invite that keeps the signed transfer invite and TF1 session code as separately validated internal contracts.
- The current Launcher is **not Authenticode-signed**. Distribution-channel and exact SHA-256 verification remain important for the current candidate.

macOS and Linux standalone launchers are not packaged as equivalent current candidates. Release readiness remains **FIELD BLOCKED**; see [`../docs/STATUS.md`](../docs/STATUS.md) and [`../release-contract.json`](../release-contract.json).
