# TeamForge Guest Launcher 0.5.1 (Windows x64)

This folder contains the WP4 standalone guest launcher. It is a .NET 10 WPF
application published as a self-contained **folder**, not a single-file app.
Extract the candidate under its short internal root; the release gate keeps
Runtime execution paths at or below 240 characters and tests a parent path
containing Korean characters and spaces.

## Trusted deployment layout

The published folder is intentionally closed over these app-owned paths:

```text
win-x64/
  TeamForge.Launcher.exe
  runtime-loader.mjs
  Runtime/
    runtime-manifest.json
    platforms/win-x64/node.exe
    backend/...
  <self-contained .NET files>
```

There is no PATH, system Node/npm, project-local runtime, source workspace, or
`TEAMFORGE_WORKSPACE_ROOT` fallback. `RuntimePins.g.cs` must be regenerated by
the packaging step after `Runtime/` and `runtime-loader.mjs` are final. A
development checkout may use all-zero placeholders before that step; those
placeholders deliberately fail runtime startup and are forbidden in a release.
The launcher verifies the compiled manifest and loader hashes, then verifies
the manifest-pinned Node executable and every allowlisted runtime file before
starting the bridge.

The runtime manifest's `guestBridgeRelativePath` must be exactly
`backend/project-peer/src/guest-orchestrator-cli.mjs`.

## Build and focused tests

```powershell
dotnet restore launcher/src/TeamForge.Launcher/TeamForge.Launcher.csproj -r win-x64
dotnet run --project launcher/tests/TeamForge.Launcher.Core.Tests/TeamForge.Launcher.Core.Tests.csproj -c Release
dotnet publish launcher/src/TeamForge.Launcher/TeamForge.Launcher.csproj -c Release -r win-x64 --self-contained true --no-restore -o launcher/win-x64
```

After packaging and pin generation, this exercises the same runtime verifier,
environment scrubber, absolute executable policy, and bridge used by the UI:

```powershell
launcher/win-x64/TeamForge.Launcher.exe --self-test-runtime
```

Success writes one JSON line with `{"ok":true,...}` and exits 0. Failure writes
`{"ok":false,"code":"..."}` and exits nonzero. The release verifier should
also set a malicious `NODE_OPTIONS` marker and confirm no marker is created.

## Security and UX boundaries

- The default managed destination is the Windows Documents known folder plus
  `TeamForge Projects`; launcher state, trust, and one-time handoff files live
  below Local AppData `TeamForge/Launcher`.
- Invite and access-code values are sent only as bounded NDJSON over stdin.
  They are never CLI arguments, persisted launcher state, or raw stderr logs.
- Trust is an explicit Publisher/Project challenge. Full Owner and Publisher
  fingerprints remain under Advanced details, including prior fingerprints on
  mismatch.
- Unity is opened only for a bridge-returned, revalidated
  `<uuid>/active/<revision>-<manifest-prefix>` path and a handoff under
  `guest-core/handoff`. The exact `ProjectVersion.txt` version is probed before
  launch. Paths are passed through `ProcessStartInfo.ArgumentList` with shell
  execution disabled.
- Legacy transfer-only invites are rejected before receive because they cannot
  complete the required realtime handoff. The Host must provide a WP4 Host
  Ready invite that keeps the signed transfer invite and TF1 session code as
  separately validated internal contracts.

macOS and Linux launchers are not packaged by this WP4 Windows field target.
